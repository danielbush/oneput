# feat: streaming syntactic split

Third approach to SYNTACTIC_SPLIT, and the one to build.

- [20260812.feat.syntactic-tokenization.md](./20260812.feat.syntactic-tokenization.md)
  — attempt 1, split-at-rest over flat sibling TOKEN's. Code on branch
  `syntactic-split-1`. Holds the settled **rule set**, which this ticket reuses
  unchanged.
- [20260813.feat.token-groups.md](./20260813.feat.token-groups.md) — attempt 2,
  a TOKEN_GROUP container. Not built. Kept because its analysis of undo,
  tombstones and motion is what showed this approach is better.

## The idea in one line

When the user types `foo-`, the `-` becomes its own TOKEN immediately and the
input shows `-`. Exactly what typing a space already does, generalised to
punctuation.

## Why this works now — the `don'` objection is dead

Attempt 1 rejected streaming because when the user has typed `don'` there is no
way to know whether an apostrophe or an opening quote is intended, so the rule
would need lookahead it cannot have.

**That objection died when the apostrophe rule was settled, and nobody noticed.**
Look at what the rule actually does:

| clause | context needed |
| --- | --- |
| word char vs punctuation → split | previous char |
| punctuation groups only with itself (`...` whole, `,"` split) | previous char |
| an apostrophe never splits | none — per character |

Every clause is **left context only**. There is nothing to look ahead for. Once
"an apostrophe never splits" is the rule, `don't` types as one TOKEN and the
ambiguity does not exist. The rule was already a streaming rule; attempt 1 built
an at-rest machine to run it.

## The mechanism

On each input change, run the splitter over the input value. If it yields more
than one part, commit all but the last as TOKEN's and keep the last in the input.

```
type "foo"   -> splitter("foo")  = ["foo"]         input: foo
type "-"     -> splitter("foo-") = ["foo","-"]     commit [foo], input: -
type "b"     -> splitter("-b")   = ["-","b"]       commit [-],   input: b
type "ar"    -> splitter("bar")  = ["bar"]         input: bar
```

Result: `[foo][-][bar]`, with **no SEPARATOR between them**, so it renders as
`foo-bar`.

This is the same shape as the existing space path — type `foo `, then `b`, and the
input shows `b`. The difference is only that a space is consumed as a SEPARATOR
while punctuation becomes content.

## Modularity — the splitter does not go in `decideInputIntent`

The risk with a streaming approach is baking punctuation rules into
`decideInputIntent` / `processUserInput`, where they would be impossible to
replace or configure later. That does not happen, because the split does not
belong there.

**The layering already exists.** `decideInputIntent` is a pure function that
answers one question: *where does this text go* — rewrite the current TOKEN,
insert after, insert before, delete. It says nothing about how many TOKEN's
result, and it should not start to.

The "text → how many TOKEN's" decision already lives one layer down, in the ops.
[ReplaceWithText.ts:27](../../packages/jsed/src/cursor/lib/ops/ReplaceWithText.ts#L27):

```ts
const [firstPart, ...parts] = text.split(/\s+/).filter(Boolean);
```

That *is* a splitter. It is hardcoded, and it is the second copy — `replaceTextNode`
has its own, `text.match(/\s+|\S+/g)`.

**So this change is a deletion, not an addition.** Replace both hardcoded regexes
with one injected function. `decideInputIntent` and `processUserInput` never gain
punctuation logic, because they never had whitespace logic to begin with.

### One interface

```ts
type Splitter = (text: string) => string[];   // whitespace runs included as parts
```

The consumer's rule is unchanged from what `replaceTextNode` does today:

| part | becomes |
| --- | --- |
| whitespace run | SEPARATOR text node |
| anything else | TOKEN |

This is also what gives no-SEPARATOR punctuation for free: `foo-bar` yields
`['foo','-','bar']` with no whitespace parts between them.

### The streaming behaviour needs no new code

Typing `foo-` produces `rewrite-current` with `inputValue: 'foo-'`, exactly as
today. `ReplaceWithText.run` splits it into two parts, creates two TOKEN's, seats
on the last, and `place` syncs the input to `-`. No new intent type, no new case
in `processUserInput`.

### Consequences worth having

- **`nullSplitter` is today's behaviour.** Whitespace-only splitting leaves the
  document provably unchanged. This is the modularity proof attempt 1's spike was
  reaching for, except now the seam is real rather than added for the purpose.
- **Three hardcoded splitters become one injected one.** A net simplification of
  the current code, independent of this feature.
- **`insertAfter` must take the separator decision from the part list** rather
  than unconditionally calling `ensureSeparatorAfter`
  ([token.ts:114](../../packages/jsed/src/lib/ops/token.ts#L114)). This is the
  same change auto-pairing will want later — see below.

Injection point: `Cursor.create({ splitter })` plus the Tokenizer, since both
consume it.

## The tokenizer uses the same splitter

`replaceTextNode` is injected with the splitter and applies it to each
non-whitespace run. Read and type paths agree **by construction**, because the
rule is left-context-only: applying it incrementally and applying it to the whole
string give the same partition.

This is what makes clicking on an untouched `foo-bar` give three stops.

## What this approach does not need

Everything attempt 2 had to solve. Recorded here so it is not re-derived:

- no TOKEN_GROUP, no taxonomy change, no `isTokenGroup` / `getGroup` / `liveParts`
- no `deriveGroup`, no derive hook in `CursorState.place`, no identity or
  `isConnected` guards
- no CURSOR motion change — TOKEN's stay flat LINE_SIBLING's
- **no undo change at all.** Each TOKEN is created once and never re-derived, so
  node identity never changes, `insertAfter` records work as-is, `merge` keeps
  collapsing keystrokes, and tombstones are untouched
- no `token.getParent` fix, no separator-inside-a-group problem, no
  `isLastText` problem

## Costs

Three, and they are the honest reason to think before building.

**1. No merge.** Delete the `-` from `[foo][-][bar]` and you keep two adjacent
TOKEN's reading `foobar`. The at-rest design re-derived the run and merged them.

Mitigated, and rather neatly: SHALLOW_TOKENIZATION already detokenizes lines that
lose the CURSOR, and re-tokenizing runs the splitter over `foobar`, which yields
one TOKEN. **The round trip is the merge mechanism**, for free. It self-heals in
the right direction, just not immediately.

The visible artifact meanwhile is one extra CURSOR stop. The document text,
rendering and save output are all unaffected.

**2. Mid-token editing.** ~~Caret in the middle of `foobar`, type `-`.
`decideInputIntent` needs a punctuation case.~~ **Did not materialise.** Typing
punctuation mid-TOKEN or at its start already produces `rewrite-current`, and
`ReplaceWithText` splits the whole input value — so the existing intent covers it
with no change. Verified by test.

**3. The rule and the mechanism become coupled.** A streaming mechanism can only
express left-context rules. Attempt 1's at-rest design kept the rule free to be
anything.

This is the architectural cost, and it is accepted: the rule settled on after four
iterations *is* a character-class automaton. Paying a permanent complexity bill —
tombstones, undo anchoring, motion, taxonomy — to buy flexibility for rules
already decided against is a bad trade.

See "Auto-pairing" below for why this cost is smaller than it first looks.

### Tests

- **`nullSplitter` leaves the document unchanged** — the existing suite passes
  with the seam in place and the rule off
- `foo-bar` typed left to right gives `[foo][-][bar]` with no SEPARATOR between
- the same text, read by the tokenizer, gives the same TOKEN's

- `don't`, `dogs'`, `'tis` stay one TOKEN while typing

## Carried over

The rule itself, unchanged — see
[attempt 1](./20260812.feat.syntactic-tokenization.md), "The rule itself".
`[\p{P}\p{S}]` counts as punctuation; word characters group freely; punctuation
groups only with itself; an apostrophe never splits, at the accepted cost that
`'quoted'` stays one TOKEN.

Still open and unchanged: ZWJ emoji tear apart (`👨‍👩‍👧`), because U+200D is
`\p{Cf}` — neither Punctuation nor Symbol, so it reads as a word character between

# Future: auto-pairing brackets

Not part of this work. Written down because it is the semantic goal behind
SYNTACTIC_SPLIT in `work/SCRATCH.md`, and because it changes how cost 3 above
should be read.

## Why cost 3 is smaller than it looks

Bracket matching sounds like the lookahead case that a streaming splitter cannot
do. It is not — because **by the time you are pairing, the brackets are already
separate TOKEN's**.

The splitter's job ends at "`(` is its own TOKEN". Pairing is then a walk over
LINE_SIBLING's, which is DOM, not text, and has no context limits at all. The two
concerns do not touch.

So isolating parens — the original motivation — is delivered by this ticket, and
everything built on top operates at the TOKEN level where jsed is already strong.

## The three behaviours

**Auto-enclose** — the CURSOR is on `foo`, the user asks for parens, and they get
`[(][foo][)]`. This is `insertBefore` + `insertAfter` of two new TOKEN's with no
SEPARATOR. Flat siblings make this trivial; a group structure would have had to be
restructured.

Over a SELECTION it is the same operation at the two ends, and `CursorSelection`
already knows its front and back.

**Auto-close** — typing `(` produces `[(][)]` with the CURSOR positioned between
them. Expressible today: seat on `(` in CURSOR_INSERT_AFTER state.

**Skip-over** — typing `)` when the next TOKEN is already `)` moves past it
instead of inserting a second one. A one-step LINE_SIBLING peek.

**Matching / deletion** — deleting a `(` may want to delete its partner. A
LINE_SIBLING walk counting depth. Again purely token-level.

## The one dependency worth knowing now

`insertAfter` ([token.ts:114](../../packages/jsed/src/lib/ops/token.ts#L114))
**always** calls `ensureSeparatorAfter`. There is currently no way to insert a
TOKEN adjacent to another with no space between them.

Every auto-pairing behaviour above needs exactly that. So the one thing to keep in
mind while doing this ticket is: **`insertAfter` / `insertBefore` will need a
"no separator" option.** Nothing else about auto-pairing constrains the present
work.

Worth noting the splitter already produces adjacent no-SEPARATOR TOKEN's, so the
*invariant* is fine — it is only the insert API that assumes a space.

## What would still need deciding, later

- Is a pair a real relationship (tracked), or is it re-derived by walking? Walking
  is cheaper and cannot go stale.
- Does auto-close trigger on typing, or only on an explicit action? Typing `(` in
  prose where no close is wanted is the usual complaint.
- Which pairs: `()`, `[]`, `{}`, quotes? Quotes are ambiguous in exactly the way
  the apostrophe rule already sidesteps, so they are probably a later question.

## Changes

- **2026-08-13** — ticket created after attempts 1 and 2 were analysed and parked.
  The decisive realisation: the settled rule set uses **left context only**, so
  the `don'` ambiguity that forced attempt 1's at-rest design no longer exists.
  That removes the reason for all the machinery attempts 1 and 2 needed —
  re-derivation, containers, derive hooks, undo anchoring, tombstone rules — and
  reduces the feature to "typing punctuation behaves like typing a space".

  Accepted cost: no immediate merge, and the rule is now permanently limited to
  left-context character-class decisions. Both judged worth it. Auto-pairing was
  checked against this and is unaffected, because pairing operates on TOKEN's, not
  characters.

  Modularity was the remaining worry — that punctuation rules would get baked into
  `decideInputIntent` and become unreplaceable. Resolved by finding that the
  codebase **already contains two hardcoded splitters**, one in `replaceTextNode`
  and one in `ReplaceWithText`, and that the intent layer has never known about
  splitting. So the work is replacing both with a single injected `Splitter`, and
  the feature is switched on by changing which splitter is injected. `nullSplitter`
  reproduces today's behaviour exactly, which makes the seam verifiable before the
  rule is turned on.

- **2026-08-13 (built)** — landed on `jsed`. It worked as designed.

  New: `src/lib/ops/splitter.ts` (the `Splitter` seam, `nullSplitter`,
  `TokenPart`, `tokenParts`) and `src/lib/ops/syntacticSplit.ts` (the rule).
  The splitter is injected at `EditorState.create` and shared by the `Tokenizer`
  and `CursorState`, so the read path and the type path cannot disagree.

  There were **five** hardcoded splitters, not two — the three insert/replace ops
  each had their own copy of `text.split(/\s+/)`. Replacing them all with the
  seam and injecting `nullSplitter` left the suite green at 621 passing, which
  confirmed the wiring before any behaviour changed. Switching the injected rule
  to `syntacticSplitter` kept the whole existing suite green as well.

  `tokenParts` returns `{ text, separatorBefore }` rather than plain strings,
  because the ops need to know *where* a SEPARATOR belongs. Each op resolves its
  own anchor gap: `ReplaceWithText` uses each part's own flag (the first part took
  over the current TOKEN), while the insert ops keep a SEPARATOR against the
  anchor TOKEN and take the flag only for gaps between inserted parts.

  Undo needed nothing, as predicted. Typing `-` after `foo` gives `[foo][-]`;
  undo tombstones the `-` and the LINE reads `foo` again; redo restores it. All
  through the existing `ReplaceWithText` / `insertAfter` records.

  Suite: 670 passing, 1 failing —
  `focusAncestorPath > marks live FOCUS mid-chain`, which was verified to fail
  identically on a stashed tree. Pre-existing and unrelated.

- **2026-08-13 (undo merging)** — the claim "undo needs no change" was too
  strong. Typing over a TOKEN with `foo-bar`, then ` baz`, then undoing left the
  hyphen in the document with **no `jsed-deleted` class**, and `bar` came back one
  character at a time.

  Both traced to `ReplaceWithText.merge`. Collapsing successive keystrokes copied
  only `next.replaceText.after` and **discarded `next.insertTokensAfter`** — so
  the TOKEN a punctuation keystroke created had no undo record at all. This bug
  predates SYNTACTIC_SPLIT (reachable by pasting multi-word text) but was rare;
  now it fired on every punctuation character. The same method's
  `if (this.insertTokensAfter.length > 0) return` guard then refused to merge the
  following keystrokes, which is why `bar` undid letter by letter.

  Fixed by carrying `insertTokensAfter` across a merge, and by letting a burst
  continue into a TOKEN the record itself inserted.

  **Where the burst ends** — an existing test (`multi-word replacement does not
  merge`) caught the first attempt, which had merged too eagerly. The rule that
  satisfies both: continue the burst into an inserted TOKEN **only when there is
  no SEPARATOR between them** (`insert.separatorAfter === null`). A SYNTACTIC_SPLIT
  boundary is invisible to the user, so `foo-bar` is one word and one undo step;
  a space is a deliberate word boundary and ends the burst. The `separatorAfter`
  field already carried this because `insertAfter` now takes the separator
  decision from the part list.

  Result: `foo-bar` + ` baz` is two undo steps, and redo round-trips exactly.
  Finer granularity later (ending a burst at punctuation) is a condition in that
  one method.

  Also added a regression test at the ops level,
  `ReplaceWithText.merge > merging keeps TOKENs inserted by the later replacement`.
  It uses the whitespace-only splitter deliberately, so it pins the *pre-existing*
  bug rather than the SYNTACTIC_SPLIT symptom. Confirmed it catches the defect by
  reverting the fix and watching it fail on `bye` surviving as live text.

- **2026-08-13 (finished)** — the three remaining items closed.

  Cost 2 ("mid-token editing needs a `decideInputIntent` case") **did not exist**.
  Typing punctuation mid-TOKEN or at its start already routes through
  `rewrite-current`, and `ReplaceWithText` splits the whole input value. Two tests
  now cover it so it stays that way. `decideInputIntent` was never touched by this
  work, which is the modularity claim holding up in practice.

  `docs/vocabulary.md` gained SYNTACTIC_SPLIT and SEPARATOR. The SYNTACTIC_SPLIT
  entry states the left-context-only constraint, since that is the one rule a
  future change could break without any test noticing.

  Exploratory demo section added, including both known gaps (no immediate merge
  after deleting a separator-less boundary; ZWJ emoji tearing) so they are visible
  rather than surprising.

  Suite: 674 passing, still only the pre-existing `focusAncestorPath` failure.
