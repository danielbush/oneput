# Declarative AppObjects

Write an AppObject as an XState machine whose states describe what Oneput shows. Each state's `meta.view` gives the layout params that every layout takes (`params`, such as `menuTitle`, `busy` and `input`) and the input `placeholder`, names a layout, fills the slots that layout adds and lists its menu rows; each row names the row builder that draws it, gives that builder's params in `params`, and gives its event in `send`; the builder decides which element raises it. A view can also declare `actions` (by action ID, with an optional key binding) and the layout's `inputSend` control; each gives an event, which the adapter sends only when the machine can take it. A view that gives `inputValue` controls the input text, for example to clear it after a submit. A `slot` function gets a second argument, the `ViewContext`: `bindingOf(actionId)` gives that action's first active key, or `undefined` when it has none. The adapter reads it from Oneput when the view renders and redraws on `bindings-change`, thus a placeholder, help text or row hint shows a rebind at once. The first render reads the keys before Oneput sets the view's own actions; their `bindings-change` then redraws, and Oneput sends the event only when the keys change, thus the redraws stop. A view can also say where focus goes when the machine enters its state: `inputFocus` (`'focused'` or `'blurred'`) for the input, and `menu.focusItem` for the row with menu focus. The adapter applies them when they change, and again after start, resume and menu open, where Oneput moves focus, and after each command (a row, an action or the send control); a redraw while the user types or moves focus keeps that focus. While the view gives `inputFocus`, Oneput does not focus the input on start, resume or menu open. An action with no `send` declines, which gives its key back to the browser; `ITEM_FOCUSED` and `INPUT_FOCUS_CHANGED` tell the machine where focus went, so it can change state. A blur does not always mean that the user left the input: the browser also blurs it when the window loses focus, or when the input element changes (for example from `input` to `textarea`). See `apps/oneput-demo/src/lib/shared/katexDeclarative/`. The machine is usually in several states at once (a parent and its active child), so the views of all the states it is in are merged, parent first, with the child's values winning. That merged view is the _active view_, and the code here turns it into Oneput calls.

- `appObjectActor.ts`: the adapter. It wraps a running actor as an AppObject: Oneput's events go into the actor, and it redraws the active view when the machine or a readable source changes (Oneput merges redraws asked for in the same turn).
- `interpreter.ts`: turns the active view into a Oneput menu, layout and input (`renderActiveView`), and defines the types a machine and its content use (`ViewDef`, `ViewSources`, `viewLayout`, `rowBuilder`, `readable`). `ViewFor<Content, Layouts, RowEvent>` gives a machine's `ViewDef` from its content and layouts.
- `oneputEvents.ts`: the standard events Oneput sends into a machine, such as `STARTED`, `BACK`, `INPUT_CHANGED`, `ITEM_FOCUSED` and `INPUT_FOCUS_CHANGED`. A row sends its own event.
- `standardLayout.ts`: a ready-made layout built on Oneput's standard layout, with a `status` slot; `StandardLayout` itself draws the `menuTitle` and `busy` params. An app can register its own layouts instead.
- `standardRow.ts`: ready-made row builders: `standardRow` for a Oneput standard menu item and `infoRow` for an information message. An app registers them, often `standardRow` as `default` (the builder for rows that name no builder), or registers its own instead.
- `signalSource.ts`: adapts a TC39 signal into a readable source, for data the machine doesn't own. Needs the optional `signal-polyfill` peer.

Tests sit in `__tests__/` as `*.test.ts`; `__tests__/*.test.types.ts` hold the compile-time checks.
