# feat: syntactic tokenization

The human's own notes live in `work/SCRATCH.md` — that is the source of truth for the
rule set and test cases. This ticket records the design conclusions reached in
discussion so they survive between sessions.

## Outcome we want

A TOKEN currently corresponds to a run of non-whitespace. We want punctuation to
form its own TOKEN's, so `foo-bar.` becomes `[foo][-][bar][.]`. Two payoffs:
editing part of a complex TOKEN becomes possible, and parens become isolated
TOKEN's — a plausible first step toward semantic handling like auto-enclosing a
selection.

Rendering must not change. There is no SEPARATOR between the resulting TOKEN's,
so `[foo][-][bar]` still reads as `foo-bar` on screen. What changes is CURSOR
granularity: three stops where there was one.

## The shape we settled on

**Split at rest, not while typing.** The naive approach — teach
`decideInputIntent` to treat punctuation like whitespace — forces the rule to be
a streaming, left-context-only decision, because when the user has typed `don'`
there is no way to know whether an apostrophe or a quote is intended. Deferring
the split until the user commits means the rule always sees a complete string,
so lookahead is legal and the ambiguity dissolves. It also means
`decideInputIntent` needs no punctuation awareness at all, and the existing
space/non-space machinery is untouched.

This mirrors INTERSTITIAL_INVARIANT: an invariant that holds at rest, established
by a pass and maintained by ops, rather than something enforced mid-keystroke.

**One shared pure function.** `splitSyntactic(text): string[]` is called from two
places, both of which see a whole string:

| path | when |
| --- | --- |
| read — `replaceTextNode` | first FOCUS / tokenization |
| commit — after typing | space, or CURSOR moves on |

Sharing one function means read-path and type-path agree by construction rather
than by discipline.

**The operation is re-derivation, not splitting.** SCRATCH's own cases require
*merging*: `foo-bar` -> `foobar` must collapse `[foo][bar]` back into one TOKEN.
So the unit of work is the maximal run of TOKEN's with no SEPARATOR between
them — concatenate its text, apply `splitSyntactic`, reconcile against the
existing TOKEN's. Split and unsplit both fall out of that, and the op is
**idempotent**, which is what makes the undo story work.

**Undo re-derives rather than recording structure.** This is the ANCHOR
normalization convention already documented in `docs/architecture.md`: a
structural `UndoRecord` re-derives derived state itself, in each replay
direction, on the region that direction produced. `retokenizeRun` has the same
properties as `anchorize` — derived, region-scoped, idempotent — so it belongs in
`normalize()` / `normalizeUndo()` rather than being a separate step. The
corollary worth stating as a rule: **UndoRecords record text, not TOKEN
structure.**

Running the split as its own step before the undo record was rejected: the user
would hit undo once to unsplit and again to revert their typing, which is two
undos for one action.

**Not an event.** Modelling commit as an observable event is what raises the
"does this run before undo?" question in the first place. It is a structural
transformation that must be atomic with the edit that caused it, so it is a
direct call inside the op. A notification can exist for the UI, but as a
consequence, not as the mechanism.

## Decisions taken

- **Stay split on re-entry.** No recompose-on-entry. Entering `[foo]` inside
  `foo-bar` gives you `foo` in the host input, not `foo-bar`. The user learns
  that punctuation-joined words are multi-unit; JOIN exists if they want to
  reassemble. Recompose was considered and parked — it restores whole-word
  editing but removes the fine-grained stops exactly when you want them.
- **Click precision needs no new machinery.** `REQUEST_FOCUS` already branches on
  `isToken` (`src/focus/Nav.ts`). First click on untokenized `foo-bar` targets
  the LINE and tokenizes, creating the sub-TOKEN's as real spans; the second
  click's `evt.target` is the exact span under the pointer. No
  `caretPositionFromPoint`, no offset mapping across a DOM mutation.
- **Commit triggers are one concept.** Exit editing, hit space, and move the
  CURSOR away are all "the CURSOR is leaving a TOKEN". One hook in `Cursor`,
  gated on a **dirty** flag so navigating past an untouched TOKEN costs nothing
  and produces no UndoRecord.
- **CURSOR landing after commit.** Land on the part containing the **input cursor
  offset** (already available in `UserInputChange.range`), scoped to the parts
  derived from the *edited* TOKEN — not the last part of the run, which may be
  content the user never touched. For the common type-at-the-end case this is the
  last derived part, so typing continues naturally.

## Open questions

- The `splitSyntactic` rule itself — see SCRATCH. Undecided: `\p{P}` alone versus
  `[\p{P}\p{S}]` (note `+ = < > $ ~ |` are Symbol, not Punctuation, so `a+b`
  would not split under `\p{P}` alone); grouping runs (`foo...` -> `[foo][...]`)
  versus one TOKEN per character; whether `don't` and backticks get an exemption.
  Deferring the split makes this a free choice rather than a constraint.
- The full commit-site list. Missing one leaves an unsplit TOKEN in the document,
  which is miserable to chase later. Should **save** force a commit on any dirty
  TOKEN as a backstop?
- **Motion must not be consumed by commit.** Confirmed by the spike, and the
  cause was narrower than expected — see Changes 2026-08-12 (spike). Resolved by
  giving `commit()` a direction.

### Commit sites still open

The spike wired the clear ones. These leak an uncommitted TOKEN because
`place()` clears the dirty flag without committing:

- **Click inside the current CURSOR_LINE.** `EditorController` calls
  `cursor.place(...)` directly for a same-line focus request.
- **`start-insert-before-current`.** Deliberately not wired. It is a genuine
  commit moment, but the landing rule would put the CURSOR on the *last* derived
  TOKEN and then `ensureSeparatorBefore` would insert a separator into the middle
  of the run. Needs the caret-offset landing rule first — with a caret at offset
  0 it resolves to the first TOKEN, which is right.
- **Selection-head walks.** `moveNext(isSelection)` / `movePrevious(isSelection)`
  skip commit, to avoid disturbing SELECTION behaviour. Probably correct, unverified.
- **Save.** Not wired; no save path was touched.

## Changes

- **2026-08-12** — design discussion. Moved from "punctuation-aware
  `decideInputIntent`" (SCRATCH's opening proposal) to split-at-rest, after the
  `don'` ambiguity showed the streaming version cannot be made consistent between
  the read and type paths. Reframed the op from split to idempotent re-derivation
  over a no-SEPARATOR run, which absorbs the unsplit cases. Undo follows the
  existing ANCHOR normalization convention. Recompose-on-entry parked.
- **2026-08-12 (spike)** — null splitter landed and the plumbing holds: with the
  identity rule the document is provably unchanged, and injecting a splitting
  stub drives the same paths. The modularity question is answered — one pure
  `SyntacticSplitter` injected at `Cursor.create`, one `commit()` choke point.

  The motion collision is real, and the cause was **not** ordering as assumed —
  committing before resolving the target was never enough. It is the **landing
  rule**. Editing `world` into `foo-bar` and pressing move-previous: commit lands
  the CURSOR on `bar` (the last derived TOKEN, per the typing rule), and the
  backward step then goes to `-` — one place back *inside the run just created*
  rather than out of it.

  So the landing rule is direction-dependent, and only the typing and space
  triggers use the caret offset. A motion trigger must land at the far end of the
  new run **in its own direction of travel**: `moveNext` lands on the last TOKEN,
  `movePrevious` on the first. `commit({ direction })` now carries this. This
  generalises the note in Decisions — "land at the caret offset" is the rule for
  commits the user did not trigger by moving.
