# feat: token groups

> **Not built. Superseded by

>

Second attempt at SYNTACTIC_SPLIT. Supersedes the mechanism in
[20260812.feat.syntactic-tokenization.md](./20260812.feat.syntactic-tokenization.md),
which stays as the record of *why* — the `don'` ambiguity, split-at-rest, the
settled rule set, and the bugs attempt 1 hit. Attempt 1's code is on branch
`syntactic-split-1`; `jsed` has none of it.

## The idea in one line

`foo-bar` stays one TOKEN to the whole codebase. It gains children, and **only
CURSOR motion knows to walk them**.

## Why this shape

Attempt 1 split a TOKEN into flat sibling TOKEN's. That destroys the original
node, and UndoRecords hold live element references — so:

> rewrite a TOKEN to `foo-bar`, let it split, press undo → **nothing, or a throw**.

`undoReplaceText` does `op.token.firstChild!.nodeValue = before`. If the split
replaced `op.token`, that node is detached and undo silently does nothing. If it
left it empty, `firstChild` is null and the `!` throws.

"Splitting is derived, so we don't record it" protects the *document* — no
SEPARATOR goes between the parts, so detokenize + normalize returns the original
text byte-for-byte and save output is unchanged. It does **not** protect the undo
stack. The damage happens on the forward pass, so suppressing the split during
replay does not help.

A container fixes this structurally: the recorded node never leaves the DOM. It
stays where it was and gains children.

**And then the key move: the container keeps answering `isToken`.** An earlier
draft gave it its own type and excluded it from `isToken`. That leaked a new
concept across the taxonomy and reintroduced the same bug one level down (see
"Why parts are TOKEN's too"). Keeping it a TOKEN confines the whole feature to
CURSOR motion.

## What it looks like

```html
<!-- typing, not yet derived: an ordinary TOKEN -->
<p>
  <span class="jsed-token">sleeping</span>
  <span class="jsed-token">foo-bar</span>
</p>

<!-- after deriveGroup: the SAME node, now holding parts -->
<p>
  <span class="jsed-token">sleeping</span>
  <span class="jsed-token jsed-token-group"
    ><span class="jsed-token">foo</span
    ><span class="jsed-token">-</span
    ><span class="jsed-token">bar</span
  ></span>
</p>
```

The outer span is the same element object, and it keeps `jsed-token`. No
whitespace inside the group, so it renders as `foo-bar`; SEPARATOR's stay outside,
between groups.

```
isToken(el)       -> true for the group AND for its parts
isTokenGroup(el)  -> has jsed-token-group
getGroup(el)      -> closest jsed-token-group, or null
```

### Why parts are TOKEN's too

Parts must be TOKEN's, not a separate type, because the CURSOR sits on them and
the seat machinery is written in terms of TOKEN's — `place()` validates
`isLineSibling`, `handleEnter` and `scrollActiveTargetIntoView` ask `isToken`.
Giving parts their own type means widening "what the CURSOR can sit on" across
the editor, which is a much bigger concept than adding a descend rule to one walk.

The cost is that both a group and its parts answer `isToken`, so anything
*enumerating* TOKEN's sees the text twice. That turns out to be one site — see
Detokenization.

## Two operations, not one

`setValue` must **not** derive. `replaceText` runs on *every keystroke* via
`rewrite-current`; if it derived, typing `don'` would split immediately and we are
back to the streaming rule the `don'` ambiguity already killed.

| | called | derives |
| --- | --- | --- |
| `setValue(token, text)` | every keystroke | no |
| `deriveGroup(token)` | at rest | yes — idempotent |

```
deriveGroup(node):
  text  = getValue(node)              // concatenates if already a group
  parts = syntacticSplitter(text)

  if parts.length == 1:
    collapse(node)                    // group-of-one -> plain TOKEN, same node
    return

  node.classList.add(jsed-token-group)
  node.replaceChildren(...parts.map(createToken))
  // safe only because tombstones never live inside a group - see
  // "Deletion and tombstones"

collapse(node):
  node.classList.remove(jsed-token-group)
  node.replaceChildren(document.createTextNode(text))

getValue(node):
  if isAnchor(node):     return ''
  if isTokenGroup(node):
    // NOT textContent - tombstones are still children. See "Deletion and tombstones".
    return liveParts(node).map(getValue).join('')       // 'foo-bar'
  return node.firstChild.nodeValue                      // 'foo'

setValue(node, text):                 // every keystroke, never derives
  if isTokenGroup(node): collapse(node)
  node.firstChild.nodeValue = text
```

`deriveGroup` reads through `getValue`, so re-deriving an existing group is
concatenate-and-re-split. **Merge falls out for free**: delete the `-` and the
parts read `foo`,`bar`; concatenating gives `foobar`; the splitter returns one
part; `collapse` fires.

## When we derive

**One rule: the CURSOR leaving a group derives it.** In `CursorState.place`:

```
const fromGroup = getGroup(from) ?? from;   // an ungrouped TOKEN is its own group
const toGroup   = getGroup(to)   ?? to;
if (fromGroup !== toGroup && fromGroup.isConnected) deriveGroup(fromGroup);
```

- **Moving between parts of the same group** — no derive. You are inside
  `foo-bar` editing `foo`; nothing shifts under you.
- **Leaving the group** — derive the whole thing. Split *and* merge, collapsing
  to a plain TOKEN if it is down to one part.

`isConnected` filters out the ops that already removed the node. This also kills
the seat-invalidation hazard: the derived unit is the one you *left*, so the new
seat is by definition in a different group.

### Space does not derive — deliberately

`start-insert-after-current` does not move the seat. It sets CURSOR_INSERT_AFTER
state and calls `ensureSeparatorAfter`. So typing `foo,` then space fires nothing;
the derive lands on the next keystroke, when `insertTextAfter` calls
`place(lastToken)`.

Attempt 1 hooked that handler and **we are deliberately not doing that again.**
It is where attempt 1's damage concentrated: the input holds an in-flight value
whose trailing space *is* the CURSOR_INSERT_AFTER signal, and the DOM has not
caught up. Both the TOKEN destruction and the `trim: false` workaround in
oneput's `InputController` came out of mutating there.

Dropping the exception also makes the model consistent rather than lagging.
Pressing space does not move the seat because you have *not left*. What you see:
`foo,` stays whole while you are still attached to it, and splits when you move
on. Arguably better than splitting under the cursor as you press space.

### Rejected: `Tokenizer.setCursorElement`

Tempting — it already sees every seat change and holds the previous element. But
it runs *inside* `onCursorChange`, after `place` has moved the seat and stamped
classes, and the Tokenizer has no way to move the CURSOR (CursorState owns a
Tokenizer, not the reverse). It can detect that a derive should happen but cannot
land the result.

# How it plays out

The point of this section is to find the holes before writing code.

## CURSOR motion — the only subsystem that must change

`getNextLineSibling` ([line.ts:119](../../packages/jsed/src/lib/core/line.ts#L119))
is a walk with two predicates:

```
shouldDescend: (node) => !isOpaque(node) && !isToken(node) && !isIgnorable(node),
pre: seat        // seat returns the node if isLineSibling(node)
```

**With zero changes, a group behaves exactly like a plain TOKEN.** `shouldDescend`
is false for it (it is a TOKEN), so the walk does not descend; `seat` returns the
group itself. Motion stops on `foo-bar` once, as today. That is a safe default —
the feature is simply off, and nothing breaks.

Turning it on is two edits to the same pair:

1. **descend into groups** — `!isToken(node) || isTokenGroup(node)`
2. **do not seat on a group** — otherwise you stop on the group *and* its first
   part, and the same text gets two stops

Three walks share this shape and all need the same treatment:
`getNextLineSibling`, `getNextLineSiblingV1`, `getFirstLineSibling` (and the
backward equivalents).

That is the whole motion change. It is confined to `lib/core/line.ts`.

## Undo — no change at all

This is what option A buys, and it is the reason for the whole design.

UndoRecords hold TOKEN references. A group **is** a TOKEN, so:

- `ReplaceWithText` records `currentToken`. That node later becomes a group. Same
  object, still a TOKEN, still `isToken`. The pointer stays live.
- `undoReplaceText` does `setValue(op.token, before)` — which collapses the group
  first, so `firstChild` is a text node again. Correct by construction.
- Undo does not need to re-derive. The next `place` that leaves the group will.

**The hole this closes.** An earlier draft had parts as non-TOKEN's and the group
as the odd type. Editing a part `foo` inside an existing group recorded *the
part*; the next `deriveGroup` calls `replaceChildren` and destroys every part, so
the record pointed at a dead node — attempt 1's bug, one level down.

Under option A the same thing happens to the part node, but it does not matter,
because **records anchor on whatever `isToken` node the op was given**, and ops
above the group line are given the group. The residual question is below.

### What the current undo system relies on

All implicit, and worth stating because the design has to respect them.

1. **Node identity is stable for the life of a record.** Records hold live
   `HTMLElement` references — `replaceText.token`, `insertTokensAfter`,
   `cursorTarget.undo/redo`. Undo and redo mutate *those exact nodes*; nothing is
   re-looked-up. A replaced node is a dead record, and it fails silently.
2. **A TOKEN has exactly one text-node child.** `undoReplaceText` does
   `token.firstChild!.nodeValue = before`. If `firstChild` is an element,
   `nodeValue` is null and the write is ignored. If it is missing, the `!` throws.
   `validate()` checks *that* there is a `firstChild`, not that it is text.
3. **Text ops record text; structural ops record nodes.** `ReplaceText` is
   `{token, before, after}`. `InsertTokenAfter` holds the created element, undo
   detaches it, redo re-attaches **the same object**. Detached-but-held nodes are
   expected to be revivable — which is exactly why a stale reference does not
   announce itself.
4. **`merge` compares node identity** —
   `this.replaceText.token === next.replaceText.token`. This is what collapses a
   burst of keystrokes into one undo step.

Consequence of (4) worth knowing up front: **if a derive swaps the node between
keystrokes, merging silently stops** and you get one undo per character. Not a
crash, just a quietly worse undo. It is an argument for the group being the thing
that persists, since the group survives every derive.

### Decision: undo anchors on the group (option a)

When the user edits a *part*, `ReplaceWithText` records the part, and
`deriveGroup` destroys it via `replaceChildren`. Two ways out were considered.

**(a) Record at group level — chosen.** The op still mutates the part; only the
record changes. Anchor on `getGroup(token) ?? token` and store the group's whole
text.

```
before: 'foo-bar'    after: 'fooX-bar'
undo:   setValue(group, before); deriveGroup(group)
```

The group node is never replaced — it only gains or loses children — so the
pointer is permanently live.

This is not a loss of granularity, as first written. Each record stores the group
text *at its own moment* and undo is a stack, so editing `foo` then `bar` then
undoing twice gives `fooX-bar` then `foo-bar`. Exact.

The real cost is that the op's **target** and its **record anchor** become two
different things: `ReplaceWithText.run` must keep replacing the *part* — typing
`foo bar` while on a part should not blow away the whole group — while capturing
before/after at the group.

**(b) Reconcile children in place — rejected.** Diff old parts against new and
mutate by index instead of calling `replaceChildren`. This preserves the pointer
but not the *meaning*:

```
before edit:  [foo]  [-]  [bar]        record: token=part0, before='foo'
you type:     [foo,] [-]  [bar]
derive:       ['foo', ',', '-', 'bar'] 4 parts vs 3
reconcile:    [foo]  [,]  [-]  [bar]   part0 reused, now holds 'foo'
undo:         setValue(part0, 'foo')   -> 'foo,-bar'   WRONG
```

After a split, part0 is only *conventionally* the first piece — the record
describes a span of text that no longer exists as one node. Reconciliation by
index is arbitrary. More code, worse outcome.

> **Still to resolve within (a): `cursorTarget` is a second node reference.**
> Every record ends in `place(this.cursorTarget.undo)`, and a seat is a *part*.
> Anchoring the text on the group is not enough — if a derive destroyed that part,
> `place` gets an orphan, `isLineSibling` still passes (it is a TOKEN, just
> detached), and the CURSOR silently goes nowhere. So (a) means **anchor both the
> text and the cursor target on the group**, or re-resolve the seat at replay time.

## Detokenization — one site, currently correct by accident

`detokenize` ([tokenize.ts:172](../../packages/jsed/src/lib/ops/tokenize.ts#L172))
is the **only** `querySelectorAll` over TOKEN's in the codebase (checked). Under
option A it matches the group *and* its parts.

It happens to work: document order puts the group first, `detoken(group)` reads
`textContent` (`foo-bar`) and replaces the group with a text node, taking the
parts with it. The loop then reaches parts that are already detached, and
`parentNode?.insertBefore` no-ops.

Working by accident is not good enough — make it explicit, either by skipping
nodes inside a group or by unwrapping groups first.

`detokenizeLineRec` is fine as-is: it hits the group, `isToken` is true, `detoken`
replaces it with its full text. Parts never get visited.

**Round trip holds**: tokenize → derive → detokenize → `normalize()` gives back
the original text byte-for-byte, because there is no whitespace inside a group.

## Save

`stripArtifacts` calls `detokenize`, so groups disappear with the same fix as
above. No new step. Worth an explicit test that save output contains no
`jsed-token-group`.

## Deletion and tombstones — the biggest hole

The current system does **not** detach a deleted TOKEN. `removeToken`
([token.ts:291](../../packages/jsed/src/lib/ops/token.ts#L291)) adds
`jsed-deleted` + `jsed-ignore` and leaves the node in the DOM;
`undoRemoveToken` resurrects it by removing those classes. Undo holds references
to these **tombstones**.

Two kinds of deletion, and only one tombstones:

| user action | path | result |
| --- | --- | --- |
| backspace within a TOKEN | `rewrite-current` → `replaceText` | text change, no tombstone |
| input hits empty | `delete-current` → `DeleteAtCursor` → `token.remove` | tombstone |

`deletionType` (char vs token) only picks `inputCursorPosition`; both tombstone.

Under groups the seat is a **part**, so emptying a part tombstones *inside* the
group. That breaks three things.

**1. `getValue(group)` cannot be `textContent`.** Tombstones are still children.
Delete the `-` from `[foo][-][bar]` and the visible text is `foobar`, but
`textContent` still says `foo-bar`. `deriveGroup` would read stale text and
re-split into three. `getValue` on a group must concatenate **live parts only**,
skipping `isDeletedToken`.

**2. `replaceChildren` destroys tombstones.** The deleted part is detached
permanently, and `undoRemoveToken` then removes a class from a node that is not
in the document — silent no-op, the text never comes back.

**3. `token.remove` on a part misbehaves anyway.** `isLastText`
([lineSegment.ts:9](../../packages/jsed/src/lib/core/lineSegment.ts#L9)) only
inspects *siblings*. A part's siblings are other parts, which are TOKEN's, so it
always returns false. Emptying the last live part of a group would never
anchorize, even if that group is the only content on the LINE — the LINE silently
loses its ANCHOR.

### Why tombstones cannot live inside a group

A tombstone works because **position encodes meaning**: the node sits where its
text belongs, so un-deleting puts the text back in the right place. Inside a
group, `deriveGroup` rewrites the children, so position is not stable.

```
[foo] [-] [bar]     delete the '-'
[foo] d(-) [bar]    tombstone in place, reads 'foobar'
derive              -> collapses to one part 'foobar'
                    -> where does d(-) live now?
resurrect           -> 'foobar' + '-' = 'foobar-'    WRONG, want 'foo-bar'
```

### The rule

**Tombstones live between groups, never inside one.**

Removing a part is a **group-level text change** — `setValue(group, newText)` then
`deriveGroup(group)` — recorded as text under option (a). Undo restores `foo-bar`
and re-derives. No tombstone involved, and the resurrection-position problem never
arises.

Tombstones stay exactly as they are for whole-TOKEN deletion at the LINE_SIBLING
level, where positions *are* stable.

Consequence: `DeleteAtCursor` needs a group branch. If the seat is a part, do not
call `token.remove`; compute the group's new text without that part and go through
`setValue` + `deriveGroup`. If that empties the whole group, fall through to the
existing whole-TOKEN path on the group — which then anchorizes correctly, because
the group *does* have real LINE_SIBLING siblings.

## SEPARATOR's and space ops — a real hole

`getSeparatorAfter(token)` uses `getNextNodeSibling(token)`.

- Called on a **group**: correct — the next sibling is the whitespace between
  groups.
- Called on a **part**: the next sibling is another part, not whitespace, so it
  returns null. Also correct, and usefully so — there *is* no separator inside a
  group.

But `ensureSeparatorAfter(part)` would **insert a space inside the group**, which
is wrong — it would break the round trip and change the rendered text.

The seat is a part, and `start-insert-after-current` calls
`ensureSeparatorAfter(sib)` with the seat. So this fires in normal use.

> **Open question.** If the CURSOR is on `foo` inside `foo-bar` and the user types
> a space, what should happen? Semantically they are splitting one word into two —
> a genuine edit, not a derived change. Probably: promote to the group level,
> break the group at that part, and insert a real SEPARATOR. That is a new op, not
> a guard. **Needs deciding.**

## FOCUS and clicking

No change, and the earlier draft's "group becomes a FOCUS stop" problem
disappears. `isFocusCandidate` already returns false for anything `isToken`, and
a group is a TOKEN.

Clicking still works for free: `REQUEST_FOCUS` branches on `isToken`, and a click
inside `foo-bar` targets the exact part span under the pointer, which is a TOKEN.
No `caretPositionFromPoint`, no offset mapping.

## `token.getParent` — a real hole

`getParent(el)` returns `el.parentElement` and is used by
`EditorController.onFocusRequestInEditingMode` to get a FOCUSABLE to exit to.

For a part, `parentElement` is the **group**, which is not a FOCUSABLE. Clicking
out of a part would exit editing to a derived artifact.

Fix: `getParent` should skip past a group — or more generally, return the nearest
FOCUSABLE ancestor rather than the literal parent.

## SELECTION

`CursorSelection` holds front/back element references and walks LINE_SIBLING's.
Two things to check:

- A selection-head walk goes through `place`, so **the derive hook must not fire
  during one** — it would mutate TOKEN's the selection is holding. Selection walks
  already pass `syncInput: false`, so the discriminator exists but must be
  threaded to the hook.
- A SELECTION whose endpoints are parts of *different* groups, or one endpoint
  inside a group. `convert()` wraps the range; wrapping across a group boundary
  may need the group split first.

## ANCHOR's

ANCHOR's are TOKEN's that survive detokenization deliberately. An ANCHOR inside a
group is undefined. Simplest rule: `deriveGroup` skips ANCHOR's outright — they
have no text to split.

`anchorize` runs over the document and inserts ANCHOR's between elements; it
should treat a group as one TOKEN, which it will, since `isToken` is true.

## Read path

`replaceTextNode` must produce groups, or a Detokenizer cycle quietly un-splits
lines the user already split. Same rule function, two callers — this is what makes
clicking on an untouched `foo-bar` give you three stops.

## Known smaller gaps

- **Group-of-one must collapse**, or editing `foo-bar` down to `foobar` leaves an
  empty wrapper. Accumulating wrappers is the failure mode.
- **`setValue` collapse flicker.** The node loses `jsed-token-group` mid-keystroke
  and regains it on the next derive. Harmless, but keep groups unstyled.
- **`validate()`** in `token.ts` throws when a TOKEN has no `firstChild`. A group's
  `firstChild` is an element — check it does not trip anything.
- **ZWJ emoji tear apart** (`👨‍👩‍👧`), because U+200D is `\p{Cf}` — neither
  Punctuation nor Symbol, so it reads as a word character between two symbols.
  Carried over, undecided.

## Changes

- **2026-08-13** — ticket created. Attempt 1 parked on `syntactic-split-1`.
  Design moved from flat sibling TOKEN's re-derived over a no-SEPARATOR run, to a
  container derived when the CURSOR leaves it. Driver: derived-ness protects the
  document but not the undo stack's element references; a container preserves them
  by construction. Dropped attempt 1's hook in `start-insert-after-current` — one
  trigger only, in `place`.

  Then a second move, which is what the ticket now describes: **the group keeps
  answering `isToken`**, and only CURSOR motion descends into it. The earlier draft
  gave the group its own type, which leaked a new concept across the taxonomy,
  made the group a FOCUS stop, and reintroduced the dangling-reference bug for
  part-level edits. Verified while checking this: there is exactly **one**
  `querySelectorAll` over TOKEN's in the codebase, and the LINE_SIBLING walks
  default to treating a group as one stop — so the feature fails safe rather than
  breaking motion.

  Holes found ahead of time and written up rather than discovered later:
  `ensureSeparatorAfter` on a part would insert a space inside the group, and
  `token.getParent` on a part returns the group, not a FOCUSABLE.

  Undo settled on option (a) — records anchor on the group while ops keep mutating
  the part. Rejected (b), reconciling children in place: it preserves the node
  pointer but not its meaning, because after a split part0 is only conventionally
  the first piece. Wrote down the four assumptions the current undo system relies
  on, since the design has to respect them; the fourth (`merge` compares node
  identity) turned up a non-obvious consequence — a derive that swaps the node
  between keystrokes silently stops keystroke merging, giving one undo per
  character. Also surfaced that `cursorTarget` is a *second* node reference in
  every record, so anchoring the text on the group is necessary but not sufficient.

  Largest hole found: **tombstones**. Deleted TOKEN's are not detached — they stay
  in the DOM marked `jsed-deleted` and undo resurrects them by removing the class,
  so undo holds references to tombstones. A tombstone works because position
  encodes meaning, and inside a group `deriveGroup` rewrites the children, so
  position is not stable. This also invalidated two things written earlier in this
  ticket: `getValue(group)` cannot be `textContent` (tombstones are still
  children, so it reads stale text), and `replaceChildren` would destroy any
  tombstone inside the group. Resolved with a rule — **tombstones live between
  groups, never inside one** — which makes removing a part a group-level text
  change under option (a). Also noted that `isLastText` only inspects siblings, so
  `token.remove` on a part would never anchorize the LINE.
